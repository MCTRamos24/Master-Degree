\begin{concept}{Four distinctions used throughout}
A security feature is not evidence that all software is secure. Passing tests is not a proof over all inputs. A mitigation can limit an exploit without removing the defect. A mature process increases confidence but does not certify a vulnerability-free product.
\end{concept}

\subsection{Course identity, scope, and assessment}
The introductory material identifies Daniele Friolo (\href{mailto:friolo@di.uniroma1.it}{friolo@di.uniroma1.it}) and directs students to the course's Google Classroom for slides, projects, and communications. Its assessment slide specifies a written examination, a \emph{possible} fuzzing-tools project with oral discussion, and an optional oral examination that can raise or lower the grade. These are the arrangements stated in the supplied slides, including their qualifications; current administrative confirmation is outside this document.

Software security studies both how software supplies protection and how software creates insecurity. The scope is broader than cryptography or network filtering: it includes language semantics, APIs, configuration, architecture, user interaction, and development practices. A correctly deployed firewall cannot repair an application that interprets a hostile request as a command.

\subsection{Why functional correctness is insufficient}
Functional requirements describe what a system should do. Security requirements restrict what it may do under adversarial conditions. An application may handle ordinary requests correctly while disclosing secrets, corrupting state, or executing unintended operations on crafted input. The attacker deliberately searches the cases that normal users and ordinary tests overlook.

The historical examples demonstrate distinct failure modes. The router-management example (CVE-2011-0352) associates a long POST value with a denial of service. The FFmpeg example (CVE-2010-4705) concerns an integer-size error in decoding. USB HID examples concern an implicit trust assumption about a connected device. Bugzilla's token example concerns insufficiently unpredictable values. The Tandberg example concerns an unnecessary passwordless privileged account. The shared lesson is not that every flaw is a buffer overflow: parsing, randomness, defaults, and trust can each undermine protection.

The worm examples illustrate that network reachability and automatic replication amplify a software flaw. Changing attacker motivations, including organized crime and state actors, affect the resources a threat model should allow. The Stuxnet reference and zero-day price illustrations motivate this point; the displayed prices are historical illustrations, not a current market survey.

\subsection{Flaws, vulnerabilities, and the platform}
\begin{definition}{Flaw and vulnerability}
A \textbf{flaw} is a defect or weakness. A \textbf{vulnerability} is a weakness relevant to violating a security policy under an attack model: the attacker needs a way to reach it and exploit its effect.
\end{definition}
Absence of a known exploit is weaker than evidence that no exploit is possible. This distinction reconciles the introduction's exploitability emphasis with the warm-up's phrase ``non-exploitable vulnerability.''

Defects arise in requirements and design as well as implementation. Configuration, deployment, and unforeseen uses of intended functionality can also create exposure. A local logic error may be visible in the code alone; a platform interaction requires knowledge of how the language, operating system, database, or browser interprets the operation. Examples include integer conversions, SQL concatenation, and memory accesses outside an object.

Software runs on an infrastructure of compilers, operating systems, libraries, runtimes, browsers, databases, and peripherals. Each layer can enforce security and each can introduce a weakness. This is the lecture's ``weakness in depth'': adding layers does not automatically create independent protection. A feature-rich stack also creates many assumptions that a programmer must understand.

\subsection{Worked exercise: the balance operations}
The image-based exercise on physical pp.~40--42 contains three different error classes. Its withdrawal uses \texttt{if (balance <= amount)} before subtracting, reversing the intended sufficient-funds condition. A negative amount can also increase the balance when subtracted. Finally, adding an unchecked positive deposit can exceed the representable integer range.
\begin{lstlisting}[language=C]
/* Core of the vulnerable slide example. */
void decrease(int amount) {
    if (balance <= amount) balance = balance - amount;
    else printf("Insufficient funds\n");
}
void increase(int amount) {
    balance = balance + amount;
}
\end{lstlisting}
For a sequential account with invariant $0\le balance\le M$, a derived withdrawal rule requires $0\le amount\le balance$. A deposit requires $0\le amount\le M-balance$, assuming the invariant before that subtraction. Checking only the comparison does not fix the domain or arithmetic issue. If concurrent requests share the balance, the check and update must also be atomic; Section~\ref{sec:race} supplies that additional obligation.

\subsection{Assets, stakeholders, threats, policies, and risk}
Start by identifying \textbf{stakeholders}, what they value (\textbf{assets}), and who or what may threaten those assets. For an online results service, records, publication authority, and service access are different assets. A student, administrator, and external attacker have different permitted actions and capabilities.

A \textbf{threat model} fixes relevant adversaries, capabilities, entry points, and assumptions. A \textbf{security policy} states permitted and prohibited behavior. A \textbf{mechanism} attempts to enforce that policy, statically or dynamically. A \textbf{risk} concerns the potential harm and likelihood of unwanted outcomes in that context. Countermeasures aim to reduce risk to an accepted level, rather than to maximize a feature count.

\begin{correction}{The CIA triad}
Physical p.~51 defines CIA as confidentiality, integrity, and availability. Page~53 instead substitutes authentication for availability. These notes use the p.~51 definition, also repeated in warm-up p.~11. Authentication remains a separate objective and often supports access control.
\end{correction}

Non-repudiation concerns evidence against an actor's denial of an action; it is not achieved merely by declaring that users cannot deny their actions. Traceability, auditing, monitoring, privacy, anonymity, and assurance add further dimensions. Which objective dominates depends on the asset and policy: the source's emphasis on integrity for financial and medical records does not establish a universal ranking over confidentiality.

The slides' four A's connect identity, access control, auditing, and action. Prevention tries to stop violations, detection tries to discover them, and reaction restores service, limits damage, and supports investigation. These are complementary. A login lockout may discourage guessing but also let an attacker deny access to a victim; evaluate the new failure mode introduced by a control.

Cryptography protects some communication and storage threats. Access control constrains principals. Type systems, memory safety, and sandboxing constrain programs. None removes the need to secure the implementation of the mechanism itself.

\subsection{Security throughout the life cycle}
The introduction describes a progression from reactive patching to regular maintenance, penetration testing, static analysis, programmer education, abuse cases, and security-aware requirements and design. These measures address different stages and should accumulate rather than replace each other. Security that is secondary in the product's functional purpose must still shape engineering decisions from the beginning.

\begin{takeaway}
Identify assets and adversaries before choosing mechanisms. Distinguish a flaw from a reachable policy violation. Consider application and infrastructure together. Combine prevention, detection, and response. Security features and successful ordinary use are insufficient evidence of adversarial robustness.
\end{takeaway}

\subsection{Programming prerequisites and small examples}
The course assumes basic operating-system/database knowledge and working familiarity with C/C++, Java, and some PHP and JavaScript. In C, allocation, pointer arithmetic, and null-terminated strings expose obligations that a managed runtime often checks automatically.

The supplied copying function contains a one-byte allocation error:
\begin{lstlisting}[language=C]
char *copying_a_string(char *a) {
    char *b = malloc(strlen(a));  /* vulnerable */
    strcpy(b, a);
    return b;
}
\end{lstlisting}
For a source string of length $n$, \texttt{strlen} excludes the terminator but \texttt{strcpy} copies $n+1$ bytes. Allocation must reserve the extra byte, check failure, and operate on a valid terminated source. The returned allocation also transfers an ownership obligation to the caller.
\begin{lstlisting}[language=C]
/* Derived correction; a must point to a valid C string. */
char *copying_a_string(const char *a) {
    size_t n = strlen(a);
    char *b = malloc(n + 1);
    if (b == NULL) return NULL;
    memcpy(b, a, n + 1);
    return b;
}
\end{lstlisting}

The pointer-summing example advances a pointer and reads four elements. Its parameter syntax \texttt{int pin[]} does not supply a run-time length check in C; the caller must provide at least four accessible integers. The Java counterpart gets null and array-index checks but still needs the intended loop bound. Its slide mixes the names \texttt{pin} and \texttt{a}; normalized code uses one name consistently. Exceptions prevent some invalid memory accesses, not arithmetic overflow or an incorrect business rule.

The object-oriented slide illustrates visibility, finality, casts, and a shallow clone. Its code is schematic rather than valid Java syntax. A shallow clone copies references to \texttt{b1} and \texttt{b2}, so both objects can still refer to the same mutable subobjects. Restricting a field's visibility does not eliminate all aliasing or unwanted effects through a shared object.

\subsection{Trusting Trust and the chain of execution}
The Ken Thompson example shows why reading application source alone does not establish what a binary does. A malicious compiler can recognize the login program and insert a backdoor. It can also recognize its own compiler source and insert both recognition rules into the next compiler binary. Removing the suspicious rules from visible source then does not remove the behavior from the existing toolchain.

The security consequence is a trust dependency: application evidence depends on the tools that translate, load, and execute it. The example does not establish that all compilers are malicious; it shows a limit of a particular assurance argument. Lecture~10 returns to minimizing the trusted computing base.

\subsection{Valid inputs versus hostile inputs}
For compression, ordinary functional validation checks
\[
\operatorname{Uncompress}(\operatorname{Compress}(f))=f.
\]
That identity says little about an arbitrary input $C$ outside the compressor's output set. The source requires invalid compressed input to produce an error instead of unsafe behavior. This is harder because the input space includes malformed lengths, structures, and encodings never generated by the companion compressor. Correct handling of expected outputs does not imply correct rejection of every other input.

\subsection{Definitions, layers of defence, and assurance}
A bug may originate in specification, coding, compilation, or another transformation. An exploit is a concrete input, command sequence, or program that takes advantage of a vulnerability. Malware is hostile code; these concepts overlap but are not synonyms. ``Threat'' in the slides sometimes denotes an adversary and sometimes a class of unwanted events; state which meaning is intended.

Programming-level controls include safer patterns and libraries, warnings, instrumentation, and checks. Operating-system controls include sandboxing, address randomization, and non-executable memory. Hardware examples include trusted modules and protected execution mechanisms. Listing such mechanisms is not a proof that their composition protects the application.

Security engineering asks what evidence justifies confidence, what remains untested, and how to prioritize work under resource constraints. Perceived safety can diverge from actual protection. Eliminating one exploit is weaker than removing the underlying vulnerability, and removing one vulnerability is weaker than eliminating an adversary's objective.

\begin{takeaway}
Track allocation size, termination, ownership, and aliases. Establish what an example actually proves. Include toolchains in trust reasoning. Secure software requires a process and a learnable engineering mindset, rather than cryptography, a special product, or network protection alone.
\end{takeaway}

\subsection{Bounds and memory management}
For \texttt{char buffer[4]}, valid indices are 0--3. Writing \texttt{buffer[4]} is outside the object. In C, undefined behavior does not promise a crash or a particular overwrite. With attacker-controlled input, a defect may corrupt a useful target under a specific implementation and layout.

The lecture also identifies dangling pointers, uninitialized memory, bad pointer arithmetic, incorrect or double deallocation, failed allocations, and leaks. A leak primarily consumes resources; a dangling pointer can let later operations access memory whose ownership or contents have changed. The absence of automatic checks makes the programmer's memory model part of the security argument.

Here ``stack overflow'' means a stack-allocated buffer overflow; exhausting the stack through recursion is a different failure.

\subsection{Unsafe string operations and termination}
\texttt{gets(buf)} does not know the destination capacity. The slides replace it with a size-aware read such as \texttt{fgets(buf, sizeof buf, stdin)}, followed by handling of errors and possible truncation. A size argument is useful only if it describes the actual object.

\texttt{strcpy(dest, src)} assumes a terminated source and enough destination space. \texttt{strncpy} is not a universal drop-in repair: copying $n$ characters from a source of length at least $n$ does not append a terminator. The source's nine-byte arrays and \texttt{"www.ru.nl"} example needs ten bytes including termination. The unterminated intermediate string then causes a later \texttt{strcpy} to read beyond it and potentially overrun the next destination.

\begin{lstlisting}[language=C]
char buf[20];
strcpy(buf, "http://");
strncat(buf, path, sizeof buf); /* wrong bound */
\end{lstlisting}
The last argument to \texttt{strncat} limits characters taken from the source, not the full destination size. If \texttt{buf} is already a valid terminated string, the available character count is
\[
\operatorname{capacity}(buf)-\operatorname{strlen}(buf)-1.
\]
This subtraction itself requires the existing length to be smaller than capacity.

\begin{correction}{The termination assignment on source p.~21}
The slide prints an inconsistent \texttt{dst[sizeof(dest-1)]} expression. For an actual array named \texttt{dest}, the intended assignment after a bounded copy is \texttt{dest[sizeof dest - 1] = '\textbackslash{}0';}. This formula does not work when \texttt{dest} is merely a pointer: \texttt{sizeof} then measures the pointer, not its allocation.
\end{correction}

\subsection{Length fields, units, and arithmetic}
The input-length exercise reads an integer, allocates \texttt{malloc(len)}, and then reads into it. Obligations include complete reads, a validated nonnegative and bounded length, conversion to the allocation API's size type, allocation success, and string termination only if a string is intended. A negative signed value can become a very large unsigned size. This does not guarantee a particular overflow by itself: the exact result depends on conversion widths, allocation success, and subsequent use.

Adding \texttt{buf[len] = '\textbackslash{}0'} after allocating only \texttt{len} bytes writes outside the allocation. Reading \texttt{len+1} bytes into it does not solve the problem either. A derived safe design reserves an extra byte after checking arithmetic, reads no more than the intended payload, checks the number actually received, and terminates inside the allocated object. Binary input may not need a terminator at all.

The Unicode exercise confuses \emph{bytes} with \emph{elements}. For \texttt{TCHAR buff[MAX\_SIZE]}, \texttt{sizeof buff} is a byte count. A wide-character API expecting an element count may therefore receive a bound larger than the array. The correct unit must match the API contract, for example \texttt{sizeof buff / sizeof buff[0]} for an actual array.

The \texttt{short len = strlen(input)} example narrows a potentially large size before checking it. A truncated or negative value can pass a comparison while the copy still uses the whole input. Keep a size in an appropriate size type and validate it before copying; do not rely on the slide's particular 32K threshold as portable across all representations.

Allocation of \texttt{count * sizeof(T)} can wrap in a fixed-width unsigned size type. For positive element size $s$ and maximum representable size $M$, require $count\le\lfloor M/s\rfloor$ before multiplying. The later copy must respect the same validated count.

\subsection{The URL-parser exercise}
The source's parser validates a URL length, then copies until a slash while skipping spaces. Three independent issues remain. A missing slash lets scanning run beyond the terminator. Testing after a post-increment can advance the pointer before the next safety check. Even a correctly bounded scan must explicitly terminate the output before \texttt{strcpy} treats it as a string.

\begin{lstlisting}[language=C]
/* Derived core pattern: src is a valid terminated string. */
size_t used = 0;
for (const char *p = src; *p != '\0' && *p != '/'; ++p) {
    if (*p == ' ') continue;
    if (used + 1 >= sizeof buff1) return; /* reject */
    buff1[used++] = *p;
}
buff1[used] = '\0';
\end{lstlisting}
This illustrates bounds and termination, not a complete URL grammar or a universal URL validator. Semantic requirements must still specify whether an absent separator or empty component is acceptable.

\subsection{Format strings as another memory-error route}
In \texttt{printf(argv[1])}, the user controls a format program, not just output text. Missing variadic arguments can lead to invalid reads; some conversions can write through pointers. The direct repair is \texttt{printf("\%s", argv[1])} after checking that the argument exists. Lecture~\ref{sec:format} explains why a destination bound alone cannot repair an attacker-controlled format string.

\subsection{Prevention, detection, and runtime mitigation}
Choose memory-safe languages where feasible, train developers, reduce unsafe interfaces, and use libraries with explicit capacities or managed strings. Fixed-size buffers require a deliberate rejection/truncation policy; dynamic buffers require allocation-failure and resource-limit handling. Historical examples include libsafe/libverify, \texttt{strlcpy}/\texttt{strlcat}, GLib strings, Microsoft Strsafe, and C++ string abstractions. Their names do not establish that every use is safe or that their historical behavior is current.

Testing and fuzzing can reveal failures; reviews and static scanners can reveal dangerous patterns. Formal verification can establish a specified memory property under an explicit model, with significant proof and modeling effort. Removing unused software or features reduces reachable attack surface.

Runtime protections include non-executable memory, address-layout randomization, instruction-set randomization as discussed in the slides, stack canaries, and protection of control data. Historical mechanisms include StackGuard, ProPolice/SSP, PointGuard, and StackShield. None establishes complete memory safety: ordinary data, function pointers, and heap objects may remain targets. Lecture~\ref{sec:defences} compares these measures in detail.

\begin{takeaway}
Track bounds, units, termination, conversion, allocation, and ownership together. A safe-looking function name does not remove caller obligations. Integer and parsing errors can enable a later overflow. Distinguish eliminating a write from detecting corruption or blocking one exploitation path.
\end{takeaway}

\subsection{Format strings are interpreted instructions}
The first argument of \texttt{printf(const char *format, ...)} describes how subsequent arguments are to be interpreted. For example, \texttt{printf("Mary has \%d cats", cats)} expects an integer. The format language is a control channel: \texttt{printf(user)} promotes an untrusted data string into that channel.

C variadic calls do not carry a general run-time count and type description for the extra arguments. If the format requests arguments that were not supplied, or interprets them with the wrong type, behavior is undefined. The lecture's observed garbage output and crashes are possible manifestations, not portable predictions. Modern calling conventions may obtain arguments from registers as well as stack locations.

Conversion & Intended operation & Misuse consequence\\\midrule
\texttt{\%d} & Format an integer in decimal. & Read a nonexistent or wrongly typed argument.\\
\texttt{\%x} & Format an unsigned integer in hexadecimal. & Potentially disclose process data.\\
\texttt{\%s} & Read characters through a string pointer. & Invalid read, disclosure, or crash.\\
\texttt{\%n} & Store the output character count through an integer pointer. & A write through an unintended pointer.\\\bottomrule
\end{tabularx}\par

\begin{correction}{Meaning of the conversions}
The source calls \texttt{\%x} uppercase; uppercase hexadecimal uses \texttt{\%X}. Lecture~3 describes \texttt{\%n} as writing ``onto the stack.'' More precisely it stores through the pointer argument; the target need not be on the stack. Exploitability requires usable argument values and a relevant layout. Missing arguments never provide a defined, universal arbitrary-write primitive.
\end{correction}

\subsection{Separating format and data}
\begin{lstlisting}[language=C]
if (argc > 1) {
    printf("%s", argv[1]);  /* fixed format, variable data */
}
\end{lstlisting}
The fixed format makes percent signs in the supplied text ordinary output. Similar obligations apply to \texttt{fprintf}, \texttt{syslog}, \texttt{sprintf}, warning/error functions, and custom variadic wrappers. The source mentions \texttt{reply} and \texttt{lreply} in wu-ftpd: an application-defined function is not safe merely because its name lacks ``printf.''

The lecture compares historical platform variants; use the exact API's documented contract rather than assuming similarly named functions are equivalent.

\subsection{Case study: cfingerd 1.4.3}
The case concerns a privileged finger daemon and an ident response received from a remote system. A lexical scanner reported ten potentially unsafe calls. Most were not exploitable in the stated path, illustrating the distinction between a suspicious call and a demonstrated attacker-controlled route.

The critical sequence first safely substitutes data into one format, then unsafely reinterprets the resulting string as another format:
\begin{lstlisting}[language=C]
snprintf(syslog_str, sizeof syslog_str,
         "%s fingered from %s", username, ident_user);
syslog(LOG_NOTICE, syslog_str);           /* vulnerable */
/* Explicitly corrected sink: */
syslog(LOG_NOTICE, "%s", syslog_str);
\end{lstlisting}
The first formatting operation does not neutralize percent conversions for a later formatter. The attacker controls \texttt{ident\_user}; the daemon's privilege makes the final logging sink security-critical.

A second flaw copies into \texttt{uname[64]} while testing \texttt{strlen(uname) < sizeof uname}. The buffer is initially zeroed, but filling its last byte removes its terminator. A subsequent length query can then read beyond it. In the illustrated layout, adjacent \texttt{buf} data becomes part of the apparent string. Later bounded formatting can truncate the remote address from the log, weakening traceability, while the expanded data contributes to the exploit path. Adjacent layout is an assumption of this case, not a general C guarantee.

The combined lesson is that individually bounded operations can compose unsafely when their contracts differ. Preserve termination, keep data out of format positions, and review logs as security-sensitive interpretation points. FormatGuard is a historical runtime-defence example in the slides, not a replacement for correcting the call sites.

\subsection{Command injection and interpreter boundaries}
Command injection occurs when data changes the program interpreted by a shell or similar engine. The source's \texttt{eval "ls \$A"} example lets a semicolon terminate the intended command and introduce another. A substitution in backticks is itself executed before the surrounding command finishes. A C program can recreate the same problem:
\begin{lstlisting}[language=C]
char buf[100];
snprintf(buf, sizeof buf, "grep %s text", argv[1]);
system(buf);                       /* interpreter sink */
\end{lstlisting}
The destination bound addresses one memory-copy issue. It does not prevent \texttt{argv[1]} from changing shell syntax. The attack's privilege is the invoked process's privilege; least privilege limits impact but does not restore the intended command structure.

The interpreter boundary is the key: bounds on the string's destination do not stop the shell from parsing attacker-controlled syntax. An API that accepts a fixed executable and separate arguments avoids this particular shell parse only when its documented contract truly does not invoke a shell; argument meaning and process privilege still need control.

The slides discuss semicolons, pipes, background execution, logical operators, command substitution, redirection, and comments. These are grammar-dependent. In shell terminology, \texttt{<<} introduces a here-document and \texttt{>>} appends output; the source's ``prepend, append'' description is imprecise. Escaping must match the actual interpreter and context. Prefer an interface that passes a fixed executable and separate argument values when its contract permits this, and validate the permitted argument meaning as well.

\subsection{Allowlisting, normalization, and validation order}
A denylist tries to enumerate forbidden values; an allowlist models the values the application accepts. The phf CGI example missed a newline in its forbidden metacharacters. A single omission can restore the attacker's grammar transition. Encodings and later decoding also defeat checks applied to the wrong representation.

The source's proposed order is to resolve encodings, cleanse, validate type/range/format, and validate semantics. It also shows that filtering can create a forbidden token: removing \texttt{d} from \texttt{adb} produces \texttt{ab}. Therefore validation must apply to the actual final representation consumed by the sink. Avoid uncontrolled repeated decoding or assuming a string is safe in every later context.

\begin{concept}{Validation is a contract, not a character ritual}
State the intended type, length, range, representation, and meaning. A permitted alphabet suitable for a username may be unsuitable for a shell argument, path component, or SQL identifier. Numeric conversion must also reject invalid syntax, overflow, and out-of-range values; a cast alone is not validation.
\end{concept}

The source's sample ``ok characters'' is illustrative, not a universal safe alphabet. Truncation can silently change a name, identifier, or security decision. Choose rejection, bounded acceptance, or truncation according to a documented semantic policy.

\begin{takeaway}
Formats, SQL, and shell strings are programs for an interpreter. Make their structure fixed and pass untrusted values through data channels. Destination bounds and cleansing solve different problems. Follow the whole path from source to sink, including intermediate transformations and logging.
\end{takeaway}

\subsection{Untrusted input is broader than a form field}
The lecture unifies buffer, format-string, command, SQL, and filename attacks as failures to enforce assumptions on external data. Untrusted input includes cookies, environment variables, uploaded files, network messages, and values returned by another service. A value's provenance matters even when it has already passed through internal code.

For command execution, the source's CGI pipeline and printer-name examples concatenate a user value into a shell command. Correcting the illustrated \texttt{snprintf} argument order is necessary for valid C, but does not solve the security problem: a bounded command string is still interpreted. Conversely, not every process-execution API invokes a shell automatically. Check the actual API, argument form, and platform rather than treating every listed function as semantically identical.

\subsection{SQL injection: how the login predicate changes}
Consider a login operation that concatenates user-supplied name and password into a query:
\begin{lstlisting}[language=SQL]
SELECT * FROM Accounts
WHERE Username = 'pippo' AND Password = 'secret';
\end{lstlisting}
The intended policy requires the matching credential pair. If the supplied name closes the quoted literal, introduces a tautological predicate, and comments out the remainder in a supported SQL dialect, the database parses a different predicate. The application can then mistake a returned row for successful authentication.

This is a parser-boundary failure, not a defect intrinsic to one database brand or application language. Comment syntax, statement batching, and operator behavior vary across configurations; the lecture's textual payloads are conceptual examples rather than guaranteed executable strings on every database.

\subsection{Prepared statements and stored procedures}
Bind values into a fixed statement instead of building syntax from them. A normalized JDBC version of the source's example is:
\begin{lstlisting}[language=Java]
PreparedStatement login = con.prepareStatement(
    "SELECT * FROM Account WHERE Username = ? AND Password = ?");
login.setString(1, username);
login.setString(2, password);
ResultSet rows = login.executeQuery();
\end{lstlisting}
The placeholder describes a value position. Quotes or SQL operators inside a bound value remain part of that value. The slides' \texttt{preparedStatement} spelling and use of \texttt{executeUpdate} for a SELECT are normalized explicitly here. The example teaches query construction, not a complete credential-storage design.

\begin{correction}{A stored procedure is not automatically a safe query}
Source p.~16 calls its example Oracle PL/SQL but mixes dialect-specific syntax and builds dynamic SQL with concatenation. Even a parameterized outer call cannot make that internal concatenation safe. The relevant property is binding values at the interpretation point; a procedure name alone supplies no such guarantee. This also qualifies the later slide's phrase ``stored procedures, if these are safe.''
\end{correction}

Prepared statements, procedure interfaces, efficiency, and network round trips are separate concerns. Evaluate the exact database and driver. Avoid concatenating values into a query before ``preparing'' it, and do not assume value placeholders cover arbitrary SQL grammar positions.

\subsection{Command and function-call variations}
The deck notes database-command injection and facilities such as SQL Server's \texttt{xp\_cmdshell}. Whether multiple commands or operating-system execution are possible depends on syntax, configuration, privileges, and installed facilities. A query-level flaw can become more serious when a powerful database account exposes additional capabilities.

The Oracle function-call example shows a different route: attacker-controlled text inside a concatenated expression can introduce a function such as \texttt{UTL\_HTTP.REQUEST}. The database then performs an operation from its own network position. Fixing one login-query shape does not cover every dynamically constructed expression.

Least privilege reduces accessible tables, operations, and optional features. It complements parameter binding and validation. Historical suggestions such as PHP ``magic quotes'' are reported as source examples, not offered here as a sufficient or current repair.

\subsection{Filename injection and directory traversal}
A path supplied by a user can select a sensitive existing file, a device, a shared temporary object, or a location outside the intended directory. Concatenating a trusted prefix with an untrusted name does not guarantee confinement when components such as \texttt{..} alter path resolution.

The possible violations span CIA: reading another user's records breaks confidentiality, changing a protected file breaks integrity, and opening an unsuitable device or resource may impair availability. A syntactic path test also does not freeze the object named by the path. Lecture~\ref{sec:race} explains how links and renames create a second, temporal problem.

The slides recommend reusing established validation and confinement mechanisms such as a chroot environment where appropriate. These require correctly configured privileges and platform assumptions; they are not substitutes for understanding path resolution and object identity.

\subsection{Prevention and detection at clear boundaries}
Identify input entry points and centralize validation obligations at well-defined choke points. Document which representation is checked, what invariants the checker establishes, and which downstream operations rely on them. Reuse reviewed validators where their contract matches the application.

Test with long, malformed, syntactically meaningful, and semantically surprising inputs. Detailed SQL errors shown to a client can reveal implementation information. Taint analysis tracks whether external data can reach a sensitive sink without an appropriate check; the lecture mentions PREfast annotations and WebScarab as historical examples of tool support. Reviews are still needed to establish that a sanitizer's guarantee matches the sink context.

\subsection{Error taxonomies and their limits}
The source lists the \emph{19 Deadly Sins} families: buffer overruns, formats, integer errors, SQL and command injection, error handling, XSS, traffic protection, hidden fields/URLs, TLS misuse, weak passwords, insecure storage, leaks, file access, name-resolution trust, races, unauthenticated key exchange, weak randomness, and poor usability. The list broadens awareness; brief mentions are not full lectures on each item.

The ``Seven Pernicious Kingdoms'' taxonomy organizes errors into input validation/representation, API abuse, security features, time/state, errors, code quality, encapsulation, plus environment. The final figure is a historical CWE hierarchy used with vulnerability records: numeric errors, insufficient validation, buffer errors, injection, path traversal, authentication, credentials, cryptography, races, and resource management occupy related branches. A CVE identifies a particular vulnerability record; a CWE identifies a weakness type. The figure's informal CVE title does not make these identifiers interchangeable.

\begin{takeaway}
Validate meaning and representation at an explicit boundary. Bind SQL values and keep the statement structure fixed. A stored procedure can recreate injection internally. Paths and temporary files require both confinement and stable-object reasoning. Taxonomies guide review coverage but do not establish safety.
\end{takeaway}

\subsection{Static, dynamic, hybrid, and operational approaches}
Static analysis examines software without executing the target program on test inputs. It includes manual reviews, lexical scanners, type checks, structural queries, and more semantic analyses. The representation may be source, bytecode, or machine code. Dynamic analysis executes particular cases and uses an \textbf{oracle} to decide whether something unacceptable occurred. Hybrid analysis uses information from both. Operational measures apply after deployment and feed observations back into engineering.

Approach & Main evidence & Main limitation\\\midrule
Static & Properties inferred from code and models. & Approximation and incomplete environment models.\\
Dynamic & Observed behavior on selected inputs. & Untested executions remain unknown.\\
Hybrid & Executions guided or interpreted with static information. & Combination still has coverage and modeling limits.\\

\subsection{Measuring reports correctly}
Let TP count true defects reported, FP count reports that are not defects, FN count defects missed, and TN count negative cases correctly rejected. Define the evaluation unit and ground truth before computing any metric.
\begin{align*}
\mathrm{TPR}=\mathrm{recall}&=\frac{\mathrm{TP}}{\mathrm{TP}+\mathrm{FN}}, &
\mathrm{FPR}&=\frac{\mathrm{FP}}{\mathrm{FP}+\mathrm{TN}},\\
\mathrm{precision}&=\frac{\mathrm{TP}}{\mathrm{TP}+\mathrm{FP}}, &
F_1&=\frac{2\,\mathrm{precision}\,\mathrm{recall}}{\mathrm{precision}+\mathrm{recall}}.
\end{align*}
These ratios need defined, nonzero denominators or an explicit convention. Precision answers how many reported items are genuine. Recall answers how many actual defects are found. The harmonic mean penalizes an imbalance; a large number of alerts does not itself imply useful recall or precision.

\begin{correction}{False-positive rate is not the chance an alert is false}
Source p.~4 gives the FPR formula correctly but glosses it as ``Probability alert is false.'' That latter quantity is $\mathrm{FP}/(\mathrm{TP}+\mathrm{FP})=1-\mathrm{precision}$. FPR conditions on actually negative cases. The negative row of the slide's table should also be read as TN for an actual negative and FN for an actual positive. The distinction follows directly from the confusion-matrix definitions.
\end{correction}

A ROC curve plots TPR vertically against FPR horizontally as a decision threshold varies. An analyst may trade additional detections for more false alarms. The source warns that representative ground-truth values are often unavailable for real tool deployments. \emph{Discrimination rate} measures paired cases: count a pair only if the tool reports the defective version and does not report its corresponding nondefective version.

\subsection{Source, executable, and human context}
Source provides names, comments, and repair locations; machine code establishes what is actually executed when source and translation differ. Proprietary components may not expose source. Bytecode preserves some higher-level structure and sits between these extremes. None removes the need to model libraries, build options, and the target environment.

Human reviewers can understand intent and policy but are costly, distractible, and subject to fatigue. The deck distinguishes an individual desk check, peer review, and structured inspection with defined roles, citing IEEE~1028. Focused questions, such as whether every protected operation checks authentication, can make a review more useful than a general request to ``find security bugs.''

Automated tools need a model: parser/extractor, intermediate representation, built-in and user rules, environment assumptions, analysis engine, and result presentation. They generally lack the full system mission and human context. Results depend on configuration, library models, and trust assumptions, not only the executable tool name.

\subsection{Types, patterns, and program structure}
Type checking can rule out classes of misuse and document intent. Use appropriately narrow types instead of weakening a type system simply to silence it. Language-specific guarantees differ; ordinary type correctness does not imply an application enforces its security policy.

The historical PMD/FindBugs comparison illustrates source-based style/defect checks versus bytecode-based defect analysis for Java. Their primary quality focus differs from a dedicated security analysis. RATS, ITS4, and Flawfinder illustrate lexical scanning: recognizing suspicious calls is fast and can work on incomplete code, but limited context produces both false alarms and missed defects. Structural queries improve on literal text search by recognizing actual call nodes such as a call whose callee is \texttt{gets}.

Knowledge-extraction tools produce architecture and asset views, dependency information, and change-impact queries. The slides name Knowledge Refinery, Rational Asset Analyzer, and Micro Focus tooling. These support understanding; they do not automatically decide whether the architecture satisfies the intended policy.

\subsection{Taint propagation: sources, transfer, and sinks}
\begin{lstlisting}[language=C]
buffer = getUntrustedInputFromNetwork();  /* source */
copyBuffer(newBuffer, buffer);           /* propagation */
exec(newBuffer);                         /* sensitive sink */
\end{lstlisting}
The source rule labels the returned value tainted. The copy rule propagates that label from input to output. The sink rule requires a suitable trust or validation property. A static tool follows possible flows; a dynamic tool attaches labels to values on observed executions. A sanitizer may remove a label only for a stated context and property. Copying or changing the variable name does not sanitize a value.

\subsection{Testing, fuzzing, and oracles}
For two 64-bit inputs there are $2^{128}$ pairs. Even an unrealistically cheap five cycles per pair on a 4~GHz processor would require approximately $1.35\times10^{22}$ years. This explains why exhaustive input testing is generally infeasible, not why testing is useless.

Functional security tests should cover both allowed and forbidden actions: unauthorized reads, invalid credentials/certificates, and other negative requirements. Statement or branch coverage identifies some omissions but is not equivalent to coverage of all security-relevant input combinations.

Fuzzing supplies many malformed, unexpected, or generated inputs and checks simple failure conditions. A crash/hang oracle is cheap. Assertions, file-state checks, memory-leak detection, and memory-access instrumentation strengthen it. The deck names Valgrind and AddressSanitizer; ASan can expose invalid memory operations on executed paths, but passing an instrumented run does not prove all paths safe.

Purely random bytes may fail an early checksum and never reach the interesting parser. Rare conditions and sequences can remain unexplored. Format-aware generation and feedback can help, but the input generator, oracle, and reachable code still determine what evidence is obtained. The source's broad statement that fuzzing finds only shallow bugs is best read as a limitation of unguided random testing in the examples, not an impossibility theorem about all fuzzers.

\subsection{Hybrid analysis, penetration tests, and deployment}
Concolic testing combines concrete runs with symbolic reasoning to guide later inputs. The cited evolutionary approach scores progress through a control-flow graph and selects/mutates inputs accordingly. Another cited study proposes security-sensitive data-flow coverage. These examples show how feedback can improve exploration; no detailed implementation of those research systems is supplied.

Penetration testing adopts an adversary's perspective under rules of engagement. Its result depends on tester skill, allowed scope, time, and environmental realism. A clean report is bounded evidence, especially if the rules exclude a realistic attack path.

Operational preparation includes useful logs, host countermeasure compatibility, sandboxing policies, and documented files/ports. The slides mention SELinux, host wrappers, EMET, firewalls, IDS/IPS, and NAT as historical examples. Do not assume the address observed at one end equals the address visible at the other. SAMATE and NAVSEA taxonomies also include requirements/design verification, assurance cases, binary/bytecode analysis, fault injection, architecture/pedigree checks, and malicious-code detection: source scanning is one part of a broader toolbox.

\subsection{Adoption and misuse}
In the RealPlayer/Helix examples, warnings were suppressed with \texttt{/* Flawfinder: ignore */} while the underlying dangerous copies remained. Optimizing for zero alerts is not equivalent to fixing defects. Suppression requires a defensible argument about the reported path.

Adopt a tool with explicit objectives, security education, a manageable pilot, a local champion, and review of outcomes. Start with relevant checks that people can understand and act on, then expand. Training must explain vulnerabilities and repairs as well as tool operation.

\begin{takeaway}
Choose tools by property and evidence, not by alert count. Know the denominators of evaluation metrics. Model source-to-sink flows and library behavior. Combine static reasoning, dynamic exploration, review, and operational feedback. A tool result has value only when someone interprets and acts on it correctly.
\end{takeaway}

\module{Program analysis and abstract interpretation}{sec:analysis}
\source{SSA - 7 - Program Analysis.pdf}{1--105}
\textit{Source author: I\c{s}\i l Dillig, University of Texas, Austin; Programming Languages Mentoring Workshop, January~21, 2014. The 105 physical pages are builds of logical slides~1--22; their footer denominator is~24.}

\subsection{Questions an analysis can answer}
Program analysis develops algorithms that infer program behavior. Applications include finding assertion failures, detecting information leaks, checking specifications, register allocation, and deciding whether loop iterations can run in parallel. The useful information depends on the question: an analysis designed for optimization is not automatically a security-policy checker.

Dynamic analysis is precise about what happened in the executions it observes, while static analysis attempts to reason across possible executions through a representation. An implementation can itself be buggy or its model incomplete, so even these descriptions are not blanket guarantees.

For an arbitrary program $P$ and semantic property $Q$, deciding whether $Q$ holds in every execution is generally undecidable. The source describes three possible compromises: return an unsound safe answer on some unsafe programs, retain soundness but raise false alarms, or permit nontermination. This is a limitation of the general problem, not a claim that every useful restricted question is undecidable.

\begin{concept}{Sound overapproximation}
Let $R$ be the concrete reachable states and let $A$ describe a superset: $R\subseteq\gamma(A)$. If the bad-state set $B$ satisfies $\gamma(A)\cap B=\varnothing$, then $R\cap B=\varnothing$. If the approximation intersects $B$, the overlap may be real or may be a false alarm introduced by abstraction.
\end{concept}

The goal is an approximation precise enough to answer the question and economical enough to compute. A division-by-zero property may need zero/nonzero information; array bounds may need numeric ranges; heap structure may need list/tree/graph properties. No single abstraction preserves every useful fact.

\subsection{The supplied sign domain}
For mathematical integers, use
\[
D=\{\bot,\mathsf{neg},\mathsf{zero},\mathsf{pos},\mathsf{nonneg},\top\}.
\]
The abstract values denote the concrete sets
\begin{align*}
\gamma(\bot)&=\varnothing,&\gamma(\top)&=\mathbb Z,\\
\gamma(\mathsf{neg})&=\{z\in\mathbb Z:z<0\},&
\gamma(\mathsf{zero})&=\{0\},\\
\gamma(\mathsf{pos})&=\{z\in\mathbb Z:z>0\},&
\gamma(\mathsf{nonneg})&=\{z\in\mathbb Z:z\ge0\}.
\end{align*}
Top means any integer is possible; it is not a large integer. Bottom means no concrete value, and is used for an unreachable state. The domain omits nonpositive and nonzero as distinct values, so some sets necessarily lose information.

Define $a\sqsubseteq b$ iff $\gamma(a)\subseteq\gamma(b)$. A lower element is more precise because it allows fewer concrete values. Two elements need not be comparable: positive and zero sets are disjoint, with neither containing the other.

\begin{center}\begin{tikzpicture}[x=1.4cm,y=1cm]
\node (top) at (0,3){$\top$};\node (nn) at (1,2){$\mathsf{nonneg}$};
\node (neg) at (-1.4,1){$\mathsf{neg}$};\node (pos) at (0.4,1){$\mathsf{pos}$};\node (zero) at (1.8,1){$\mathsf{zero}$};\node (bot) at (0,0){$\bot$};
\foreach \a/\b in {bot/neg,bot/pos,bot/zero,pos/nn,zero/nn,neg/top,nn/top}{\draw[burgundy,thick](\a)--(\b);}
\end{tikzpicture}\end{center}
\diagramcaption{The six-element sign lattice orders abstractions by the concrete values they represent.}

The \textbf{join} $a\sqcup b$ is the least upper bound: the most precise domain element that covers both possibilities. Thus
\[
\mathsf{pos}\sqcup\mathsf{zero}=\mathsf{nonneg},\qquad
\mathsf{pos}\sqcup\mathsf{neg}=\top,\qquad
a\sqcup\bot=a.
\]
The meet is the greatest lower bound. In this finite domain every subset has a least upper and greatest lower bound; it is a complete lattice.

\subsection{Abstraction, concretization, and the almost-inverse laws}
The abstraction $\alpha:\powerset(\mathbb Z)\to D$ selects the most precise representable superset of a concrete set. The examples are
\[
\alpha(\{2,10,0\})=\mathsf{nonneg},\quad
\alpha(\{3,99\})=\mathsf{pos},\quad
\alpha(\{-3,2\})=\top.
\]
These are not exact representations of the input sets: for example, nonnegative also permits~1 and many other values. The slide's almost-inverse equations, visible in its diagram, are
\[
\alpha(\gamma(a))=a,\qquad C\subseteq\gamma(\alpha(C)).
\]
An abstract value survives concretization and reabstraction unchanged, while concrete information may be lost. With the order and monotonicity of these maps, this is the Galois-insertion relationship used by the source. Equivalently for this construction,
\[
\alpha(C)\sqsubseteq a\quad\Longleftrightarrow\quad C\subseteq\gamma(a).
\]
This equation connects a claim in the abstract domain with a containment claim about concrete values.

\subsection{Abstract semantics}
A concrete state maps variables to values. An abstract state maps them to domain elements, representing allowed signs. A statement transformer describes how an operation changes a state. For a concrete transformer $f$, soundness of its abstract counterpart $f^\#$ requires
\[
f(\gamma(a))\subseteq\gamma(f^\#(a)),
\]
with state-set lifting understood. Thus an abstract operation may add impossible outcomes but must not discard a possible concrete outcome.

For $x=y+z$, use the source's sign-addition table:
\begin{center}\small
\begin{tabular}{@{}c|cccccc@{}}\toprule
$+^\#$ & $\mathsf{pos}$ & $\mathsf{neg}$ & $\mathsf{zero}$ & $\mathsf{nonneg}$ & $\top$ & $\bot$\\\midrule
$\mathsf{pos}$ & $\mathsf{pos}$ & $\top$ & $\mathsf{pos}$ & $\mathsf{pos}$ & $\top$ & $\bot$\\
$\mathsf{neg}$ & $\top$ & $\mathsf{neg}$ & $\mathsf{neg}$ & $\top$ & $\top$ & $\bot$\\
$\mathsf{zero}$ & $\mathsf{pos}$ & $\mathsf{neg}$ & $\mathsf{zero}$ & $\mathsf{nonneg}$ & $\top$ & $\bot$\\
$\mathsf{nonneg}$ & $\mathsf{pos}$ & $\top$ & $\mathsf{nonneg}$ & $\mathsf{nonneg}$ & $\top$ & $\bot$\\
$\top$ & $\top$ & $\top$ & $\top$ & $\top$ & $\top$ & $\bot$\\
$\bot$ & $\bot$ & $\bot$ & $\bot$ & $\bot$ & $\bot$ & $\bot$\\\bottomrule
\end{tabular}\end{center}
For example, positive plus positive is positive; positive plus negative may have any sign. Nonnegative plus positive is positive. Bottom is absorbing because an impossible operand combination has no results. A nonrelational environment can lose relationships between variables; if two operands alias the same value, treating them independently can be sound but less precise.

\begin{technical}{The arithmetic model is part of the proof}
This sign table models mathematical integers. A finite-width unsigned sum can wrap and a signed C overflow is not ordinary integer arithmetic. To transfer this proof to machine code, prove that the relevant arithmetic stays in range or use abstract semantics for the language's actual arithmetic. Lecture~8's wraparound examples explain why this assumption matters.
\end{technical}

\subsection{Control-flow joins and fixed-point iteration}
Loops introduce recursive dependencies between states. Build a control-flow graph (CFG) of basic blocks and edges. For each block $b$, combine predecessor outputs and apply its abstract transfer:
\[
\operatorname{in}[b]=I_b\sqcup\bigsqcup_{p\in\operatorname{pred}(b)}\operatorname{out}[p],
\qquad
\operatorname{out}[b]=f_b^\#(\operatorname{in}[b]).
\]
$I_b$ supplies the initial state at the program entry and is bottom elsewhere. If edge conditions are modeled, they refine the corresponding predecessor state before the join. Initialize states to bottom, propagate, and repeat until no value changes. Joins retain both paths even when their exact relation is lost.

The intermediate approximations start below the eventual solution and need not yet cover every execution. The final stable solution, given sound transfers and properly modeled entry states, is an overapproximation. Confusing these two facts would incorrectly certify a program before its loop back-edge has been considered.

\subsection{Worked loop and the slide-build sequence}
The diagram and iterative builds analyze the following initialization and loop:
\begin{lstlisting}[language=C]
x = 0; y = 1;
while (y <= n) {
    if (z == 0) x = x + 1;
    else        x = x + y;
    y = y + 1;

\end{lstlisting}
The target question is whether $x$ is always nonnegative in the loop. No useful assumption about $z$ or $n$ is needed for this invariant under mathematical-integer arithmetic.

\subsection{Termination and widening}
For a finite CFG, monotone propagation over a finite-height lattice can increase a state only finitely many times. The six-element sign domain therefore gives a terminating iteration. More expressive domains may contain infinite ascending chains and require convergence acceleration such as widening. A widened result is chosen to reach a sound stable overapproximation; it need not equal the least fixed point obtained without acceleration.

\begin{correction}{Completeness is not a finite-convergence condition}
Source pp.~95--98 claim that a complete lattice ensures termination and link the need for widening to absence of completeness. Completeness ensures the required suprema exist; it does not forbid an infinite ascending chain. For example, the complete lattice $\powerset(\mathbb N)$ contains
\[
\varnothing\subset\{0\}\subset\{0,1\}\subset\{0,1,2\}\subset\cdots.
\]
A transfer that repeatedly adds the next natural number never stabilizes in finitely many such steps. Finite height or a suitable ascending-chain condition is the relevant sufficient condition for the basic iteration here. This distinction is also supported by Cousot and Cousot's primary discussion of finite/chain-condition domains versus infinite domains with widening (Appendix~\ref{app:refs}).
\end{correction}

\subsection{Precision choices}
The final slide identifies several design choices. A flow-sensitive analysis associates facts with individual program points; a flow-insensitive one summarizes more globally. A path-sensitive analysis preserves distinctions between paths that a simple join would merge. Forward analysis propagates consequences from entry facts; backward analysis propagates requirements from a goal or later point. These choices affect cost and precision, while soundness still depends on the actual semantics and implementation.

\begin{takeaway}
Choose an abstraction for a stated property. Order abstract values by the concrete sets they permit. Use sound transfer functions and joins at control-flow merges. Consider back-edges until the result stabilizes. Separate least-fixed-point existence, finite convergence, and a proof about the concrete program.
\end{takeaway}

\source{SSA - 8 - BO Defence.pdf}{1--35}
\subsection{Layers of defence and trade-offs}
The lecture separates engineering practice, patching/signatures, language mechanisms, analysis, compiler instrumentation, and operating-system support. These controls act on different parts of the failure chain.
\par\noindent\begin{tabularx}{\linewidth}{@{}>{\raggedright\arraybackslash}p{28mm}YY@{}}\toprule
Layer & Contribution & Residual limitation\\\midrule
Inspection and documentation & Expose assumptions and unsafe operations; support reuse. & Require time, expertise, and access to relevant code.\\
Patches & Remove or reduce a known vulnerability. & Availability and deployment delay; an exploit-specific patch may leave a broader defect.\\
Attack signatures & Recognize known input or behavior patterns. & Updates required; unknown/variant attacks may evade them.\\
Safer languages and libraries & Enforce bounds or provide managed objects. & Migration, interfaces, resources, and exception policy remain.\\
Static and dynamic analysis & Detect suspicious paths or executed invalid accesses. & Approximation, test coverage, and model limitations.\\
Compiler/OS controls & Detect corruption or obstruct an exploit path. & Do not establish full memory safety; may turn a compromise into a crash.\\\bottomrule
\end{tabularx}\par

The source's overhead and language-performance comparisons are historical observations about particular approaches. They are not measurements of every current implementation. A defence's cost must be assessed for the target workload and threat model.

\subsection{Language and library approaches}
Managed languages can prevent ordinary unchecked accesses beyond an array. Safer C-like dialects, exemplified by Cyclone, try to retain low-level expressiveness with stronger pointer rules. Porting can require code changes, recompilation, and toolchain adaptation. The historical source identifies debugger and pointer-syntax difficulties; it does not supply a modern tool-support survey.

``Safe'' buffer abstractions may reject oversized data, grow the buffer, truncate, or raise an exception. Those choices have different security semantics. Growth can exhaust memory; truncation can change an identifier; termination can allow denial of service. A library that wraps strings but leaves other low-level operations unchecked does not cover every route to an overflow.

Static scanning helps find unsafe calls but does not make every report a true defect. Dynamic memory instrumentation can detect invalid accesses even when the program's visible result seems normal. It still depends on executing a relevant path.

\subsection{Non-executable memory and code reuse}
Marking stack/heap data non-executable blocks a class of attacks that inject executable bytes into those regions. It does not prevent the overwrite itself. The source's return-into-libc example redirects control into already executable library code such as a command-execution routine. That route does not require executing code from the data buffer.

Address randomization makes useful target locations less predictable; information disclosure may weaken that uncertainty. Hardware-supported bounds/interrupt schemes aim to detect illegal accesses, but an implementation must track the relevant object bounds and define its reaction. Merely knowing an address is in mapped memory is weaker than knowing it is inside the intended object.

An IDS might recognize abnormal system-call sequences, such as an unexpected execution call. Detection can lead to termination and retain a denial-of-service outcome. A response policy must balance containment and service continuity rather than treating every abort as successful preservation of all security objectives.

\subsection{Stack canaries, read-only return data, and bypasses}
A compiler places a guard value between a vulnerable region and saved control data, then checks the guard before returning. Random guards reduce guessability; terminator characters can interfere with some string-copy attacks. Historical implementations include StackGuard, SSP, and Visual C++ \texttt{/GS}.

\diagramcaption{A stack canary can detect some overwrites before return, but does not prevent all corruption.}

If an overwrite crosses the guard and changes it, the check can detect that corruption before a return through the damaged address. However, ``unchanged canary iff unchanged return address,'' posed in the slides, is not a general theorem. An attacker may know and restore the guard, exploit an indirect write, or overwrite a local function pointer and use it before the return check. Heap targets and ordinary non-control data may never cross this guard.

The source also discusses making return-address pages read-only (MemGuard) and trapping writes. Coarse page granularity can impose overhead because legitimate stack updates share those pages. The placement, integrity, and lifetime of reference guard values are also part of the trusted mechanism.

\subsection{Fixed-width unsigned arithmetic}
For an unsigned $w$-bit integer with values $0,\ldots,2^w-1$, arithmetic is reduced modulo $2^w$. In the source's eight-bit examples,
\[
255+1\equiv0,\qquad16\cdot17\equiv16,\qquad0-1\equiv255\pmod{256}.
\]
A length check can therefore wrap before the comparison. Suppose a buffer has capacity $B$ and the code tests $a+b+1\le B$. If the sum wraps to a small value, the test may pass although the intended concatenation is too large. A derived overflow-avoiding test is
\[
a<B\quad\text{and}\quad b\le B-1-a,
\]
evaluated in that order in an appropriate unsigned size type. It reserves a byte for termination without first forming the risky sum.

\begin{lstlisting}[language=C]
/* Derived bounded concatenation; s1/s2 supply len1/len2 bytes. */
if (len1 >= sizeof buf) return;
if (len2 > sizeof buf - 1 - len1) return;
memcpy(buf, s1, len1);
memcpy(buf + len1, s2, len2);
buf[len1 + len2] = '\0';
\end{lstlisting}
This focuses on capacity arithmetic and requires valid source ranges and nonoverlapping objects for \texttt{memcpy}. It does not validate the semantic content of either input.

\begin{correction}{The concatenation and unterminated-string exercises}
Source p.~31 uses \texttt{0xFFFFFFFF} as the maximum size; its wraparound example assumes a 32-bit size type. The same literal does not wrap a 64-bit \texttt{size\_t} in that sum. Its initial \texttt{strncpy} also need not terminate the destination before \texttt{strncat}. On p.~32, copying ten nonzero characters into a ten-byte array already removes termination, so a subsequent \texttt{strlen} is not guaranteed to return~10: it can read outside the array. Explain this prior defect before the unsigned-subtraction problem the slide intends to illustrate.
\end{correction}

Using an unsigned size type avoids some negative-size mismatches but does not make subtraction or addition safe. Check range and overflow explicitly. Signed C arithmetic has different rules; it is incorrect to generalize unsigned modular behavior to all signed operations.

\subsection{Managed code and native dependencies}
Java's checked array operations prevent the ordinary C-style buffer overwrite in correctly functioning managed execution. A Java application can still load a native library, as in the source's packet-driver example. An unchecked native formatting operation can corrupt a native buffer and undermine the combined application. A language guarantee applies at its enforcement boundary, not automatically to every component it calls.

\begin{takeaway}
Compare defences by the defect they remove, the exploit step they block, and the property left at risk. Canaries and non-executable memory are complementary and incomplete. Correct capacity arithmetic is necessary even with bounded copies. Include native dependencies in a managed application's threat model.
\end{takeaway}

\module{SQL injection, signatures, and defensive query construction}{sec:sql}
\source{SSA - 9 - SQL injection.pdf}{1--14}
\subsection{Database background relevant to injection}
A relational database organizes records into named tables and columns. \texttt{SELECT} queries return a result set; \texttt{UPDATE}, \texttt{INSERT}, and \texttt{DELETE} change records. Data-definition operations such as \texttt{CREATE TABLE}, \texttt{ALTER TABLE}, and \texttt{DROP TABLE} alter schema. Privilege to read a table is distinct from privilege to change or remove it.

The slide's user table contains illustrative weak plaintext credentials. Its purpose is to explain query interpretation; it is not an endorsed authentication architecture. Its SQL99 ``most current standard'' statement is historical and must not be read as current standards information.

\subsection{The vulnerable login and why signatures miss variants}
The source concatenates name and password into quoted SQL literals. Closing a literal and changing the WHERE expression can turn an identity check into a tautology, as explained in Section~\ref{sec:validation}. The defect is the application constructing unintended SQL grammar; replacing the database vendor or the web language alone does not repair it.

\subsection{Why escaping alone is fragile}
The lecture critiques generic quote escaping such as \texttt{addslashes}. A string transformation has a particular encoding and grammar contract. It may not cover a numeric expression, a different literal form, or a later decoding stage. Signature evasion and input-filter evasion share this mismatch between a surface pattern and the language the sink actually interprets.

Allowlisting remains useful for application meaning, such as a bounded numeric identifier, but it complements the structural separation provided by bound parameters. A blacklist of dangerous keywords should not become the main argument that arbitrary concatenated SQL is safe. This resolves the tension between the deck's early signature discussion and its later keyword-filter suggestion.

\subsection{Parameterization and least privilege}
The final source example replaces concatenation with a fixed SQL command and named parameters. The same principle applies to JDBC's positional placeholders: the database receives the intended statement structure and separate value bindings.
\begin{lstlisting}[language=SQL]
SELECT * FROM Users WHERE login = @Name AND password = @Password;
\end{lstlisting}
Here \texttt{@Name} and \texttt{@Password} denote the source's parameterized API convention, not portable parameter syntax for every SQL engine. Correct binding at this boundary is the relevant defence; internally concatenated SQL in a stored procedure can reintroduce the flaw.

The lecture also recommends restricting the database identity, stored procedures, tables, and optional operating-system facilities to what the application needs; hiding raw ODBC/OLE DB errors from clients; logging access and failed object attempts; and validating inputs. These measures bound damage and improve detection. They are layers around correct query construction, not substitutes for it. Its IDS title refers to the signature-evasion discussion; the slides do not teach a complete IDS architecture.

Run the application with a database identity that can access only necessary objects and operations. Restrict optional procedures and operating-system facilities. Return controlled error responses, retain useful internal logs, and monitor failed access attempts. Error suppression reduces disclosure but does not remove injection; lecture~10 shows that differences in results or timing can still reveal information.

\begin{technical}{What the IDS title covers}
The deck is titled ``SQL Injection and IDS,'' but its IDS material is a short comparison of signature evasion and input-validation circumvention. It does not supply a full IDS architecture or algorithm. These notes preserve that scope rather than inventing an IDS chapter.
\end{technical}

\begin{takeaway}
The important boundary is SQL structure versus data values. Surface signatures are evadable and dialect-specific. Combine correct binding, semantic validation, least privilege, controlled errors, and monitoring. None of the last three compensates for an injection-prone query.
\end{takeaway}

\module{Security design principles}{sec:principles}
\source{SSA - 10 - Design Principles.pdf}{1--54}
\subsection{Principles as questions for a concrete system}
Security principles apply inside a method, between application components, at the OS/network boundary, and within an organization. They overlap and sometimes conflict. A useful review connects each principle to an asset, failure mode, and actual design decision instead of merely checking that its name appears in documentation.

\subsection{Secure the weakest link and use defence in depth}
An attacker can choose an inexpensive route to the objective. Strong transport encryption does not protect a compromised endpoint or an exposed customer database. The lecture's credit-card example therefore emphasizes a risk analysis across the whole path rather than assuming the network is always the weakest part.

Defence in depth places complementary controls on the path. A firewall, a robust web application, and a restricted application account address different failures. Filesystem access control plus encryption can cover different exposures when a laptop, removable device, or discarded disk leaves the original environment. The source calls changing environmental assumptions ``environmental creep'': a machine that once stayed inside the perimeter may later be carried outside it.

Multiple controls should not be mistaken for independent controls if they share the same failure cause. Their combined argument should identify what remains protected after one is defeated. Availability also remains a requirement: simply disabling a system is not a useful universal security design.

The historical world-readable password-file example motivates protecting stored hashes as well as transforming passwords. The Sun tarball case illustrates another route: a reused, uncleared heap buffer can disclose fragments of earlier sensitive content. The intended repair is to initialize the output buffer and ensure only initialized, intended bytes are serialized. The slide's abbreviated \texttt{calloc(BUFSIZE)} spelling is not a complete C call; the relevant form has two size arguments, such as \texttt{calloc(1, BUFSIZE)}, with failure checking.

\subsection{Least privilege and compartmentalization}
Grant a principal, process, or module only the permissions it needs. Resource, file, network, and administrative permissions all count. Running every service as root, sharing administrator credentials, or exposing an unnecessarily public member expands the possible damage and the number of interactions that need review.

The Java policy and visibility examples show this at two scales: avoid all-permission grants, and restrict class/member interfaces. Compilers often complain when access is too narrow but do not complain when it is needlessly broad; tightening privilege therefore requires deliberate review or suitable analysis. The source names JAMIT as a historical visibility-tightening example.

Fine-grained privilege rules can become complex. Compartmentalization divides a system into comprehensible regions with small interfaces, containing a failure inside a region. Examples include separate machines, accounts, filesystem confinement, virtual machines, and sensitive modules. Boundaries have different strengths: separate accounts still share an operating-system kernel, and separate virtual machines still depend on their isolation mechanism.

\node[box] (web) {Public web\\component};
\node[box,right=of web] (api) {Restricted\\interface};
\node[box,right=of api] (db) {Protected\\data component};

The slides contrast hosted hardware simulation with a hypervisor beneath guest operating systems. Their security lesson is where isolation is enforced and what must be trusted. The terms hypervisor and microkernel are not generally synonymous; these diagrams are simplified architectures rather than a complete virtualization taxonomy.

\subsection{Minimize attack surface, including exposure time}
Reduce unnecessary sockets, services, dynamic endpoints, privileged accounts, weak file permissions, and exposed interfaces. At code level, narrow visibility can simultaneously reduce privilege and the set of reachable operations.

Exposure also has a time dimension. Automatic session/screen locking, disconnecting unused services, and clearing sensitive buffers after use shorten opportunities for misuse. Such choices need a usability and operational policy: a short timeout can disrupt legitimate work, and deleting data affects intended availability.

\subsection{Secure defaults and secure failure}
Default configurations should turn on protection and deny permissions until justified. Users who retain the default then receive the intended protection. A feature enabled everywhere by default expands the attack surface even for users who never need it.

Failures require equally explicit policy. The lecture's administrator-mode example sets \texttt{isAdmin=true} before a risky operation and logs inside the exception handler before resetting it. If logging itself fails, the reset may not run. Restoring a safe privilege state must not depend on the success of unrelated cleanup. A structured cleanup path or scoped privilege design makes the obligation visible.

\begin{lstlisting}[language=Java]
/* Derived control-flow illustration, not a complete privilege API. */
isAdmin = true;
try {
    privilegedOperation();
} finally {
    isAdmin = false;
}
\end{lstlisting}
In a real concurrent system, a shared boolean is not itself an adequate privilege boundary. The example illustrates restoration on exceptional exits, not an endorsement of the source's simplified authorization mechanism.

Other failure cases include ignoring a negative C return value, treating \texttt{strncpy}'s returned destination pointer as proof of termination, swallowing every exception, and catching many unrelated exception types in one recovery path. If impersonation fails but a privileged service still deletes a file, the operation may run as the service rather than the intended restricted user. Check the identity-changing operation before using the assumed identity.

The historical OpenSSH/OpenSSL example concerns failure to obtain the expected randomness source. The important rule is to detect failure and fail safely; replacing one device name with another is not a general platform-independent cryptographic design. Likewise, falling back to weaker security for compatibility must be a deliberate, justified policy rather than an accidental error path.

\subsection{Privacy, error channels, and blind SQL injection}
Version banners and detailed errors disclose information useful to an attacker. Hiding those details reduces one observation channel, but a vulnerable system can still leak a predicate through normal behavior.

For a numeric item identifier concatenated into SQL, the lecture compares a true condition with a false one. If the returned page changes, the attacker has learned one bit about the database. Conditional errors create another channel. Conditional expensive operations can create a timing channel even when every visible error page is identical. This is \textbf{blind SQL injection}: the attacker infers information from indirect effects rather than a directly displayed query result. Fix the injection boundary; standardizing errors alone cannot close these other channels.

\subsection{Open knowledge, usability, responsibilities, and assumptions}
Do not base protection on attackers never learning the design. The source invokes Kerckhoffs's principle and warns against hardcoded secrets, hidden URLs, and client-side passwords. Appropriate secret keys can remain secret even when mechanisms are public; obscuring code does not establish that separation.

Use community knowledge to identify known weaknesses and established solutions for the chosen language, platform, and application. The lecture's warning against designing or implementing one's own cryptography emphasizes reuse of reviewed mechanisms and correct integration. Copying an unreviewed internet snippet is not the same as adopting a sound community resource.

Psychological acceptability means users can understand and routinely follow protection. Cumbersome mechanisms invite workarounds. Education helps but cannot compensate for an unusable workflow indefinitely.

Assign responsibility for checks explicitly. For \texttt{process(String str)}, specify whether the caller or callee rejects null or empty input. Defense in depth may justify both checks, but responsibility should not disappear because both parties assume the other performs it.

Write down assumptions, including seemingly obvious ones: users may be automated, machines may move outside a firewall, allocation may fail, and code may consume all CPU. A protocol message's syntactic validity does not establish the sender's benign intent.

\subsection{Trust and the trusted computing base}
The \textbf{trusted computing base} (TCB) is the hardware/software whose correct behavior the security argument relies on. ``Trusted'' describes a dependency; ``trustworthy'' describes justified confidence. Minimize the TCB and understand dependency chains, including the compiler example in Section~\ref{sec:warmup}. Trust in a component can import dependencies on its tools and platform; this does not make trust an unconditional mathematical transitive relation in every context.

\begin{takeaway}
Apply principles to concrete decisions and counterexamples. Use layers with distinct roles, narrow privileges, and enforced compartments. Define safe states before errors occur. Reduce disclosure without relying on obscurity. Document responsibilities and trust assumptions, then challenge them with an adversary's choices.
\end{takeaway}

\module{Race conditions and time-of-check/time-of-use flaws}{sec:race}
\source{SSA - 11 - Race Conditions.pdf}{1--25}
\subsection{Concurrency invalidates sequential assumptions}
The source describes shared access, at least one modifying actor, and missing enforcement of the required ordering. A race condition exists when correctness depends on an order the program does not guarantee. A data race is the more specific unsynchronized conflicting-access concept used by a language memory model; the terms should not be treated as exact synonyms. A TOCTOU flaw can exist across separate operations on a filesystem or database even when there is no ordinary shared-variable data race.

Preemption can occur between a check and the operation that relies on it. Making that interval short does not eliminate it. An attacker can repeat attempts or influence timing; a bug that appears rarely in ordinary use may be deliberately amplified.

\subsection{The servlet counter and atomic updates}
\texttt{count++} is conceptually a read, addition, and write. Moving it into \texttt{println(++count)} does not make the update atomic. For initial \texttt{count=0}, an illustrative interleaving is:
\begin{center}\begin{tabular}{@{}cll@{}}\toprule
Step & Thread A & Thread B\\\midrule
1 & Read 0 & \\
2 & & Read 0\\
3 & Store 1 & \\
4 & & Store 1\\\bottomrule
\end{tabular}\end{center}
One increment is lost; a serialized order would produce~2. This simple model illustrates the defect and does not enumerate every behavior a language memory model might permit for unsynchronized code.

The lecture first synchronizes the whole servlet method, then shortens the protected region:
\begin{lstlisting}[language=Java]
int myCount;
synchronized (this) {
    myCount = ++count;
}
p.println(myCount + " hits so far!");
\end{lstlisting}
The shared update and capture belong in one critical section. Output can use the local snapshot outside it. All relevant accesses must obey the same locking discipline. \texttt{synchronized} excludes threads competing for the same monitor; it does not globally serialize every synchronized block on every object.

\subsection{Check, decide, and act as one protected operation}
In the bank-account example, two requests can both observe enough funds, then both spend them. A lock or transactional design must cover the decision and the state update, not merely each read or write in isolation. The invariant is about the relationship between balance and authorized payment, not just the atomicity of a machine load.

Creating a world-writable file and tightening permissions afterward exposes a similar window. Set restrictive creation permissions from the start under the appropriate platform contract; do not assume an immediate later \texttt{chmod} removes the intermediate state.

\subsection{Filesystem names, links, and TOCTOU}
The source's historical privileged \texttt{mkdir} creates a directory and later changes ownership. If an adversary can replace the named object between those steps, the privileged operation may act on a different target. The narrative depends on an early implementation's resolution and permission behavior; it is not a claim about every present-day \texttt{mkdir}.

The \texttt{access(filename, R\_OK)} then \texttt{open(filename, O\_RDONLY)} example makes the same point. The second lookup can refer to another object after a rename, removal, or link change. Also, the relevant access-check identity must match the intended policy, especially in privileged programs. A successful prior path check is not a durable capability to the later object.

The top route is the time gap: a pathname is a name that can resolve differently on a later lookup. The lower route captures the lecture's recommendation to verify the actual opened object and use stable handles, with exact mechanics depending on the platform and operation.

Use atomic platform operations where possible, bind later work to an opened descriptor/handle, and verify the necessary properties of that actual object. The exact safe sequence depends on whether creation, ownership, links, and privileged identities are involved. Locking a local application object does not prevent an unrelated process from renaming a shared path.

Predictable temporary names, public writable directories, and repeated path lookups are review warnings. The deck's \texttt{lpr} and Solaris \texttt{at} examples combine time-dependent replacement with dangerous delete operations or path traversal. These are reasons to review both name semantics and operation ordering.

\subsection{Buffers, information flow, and failure reproduction}
The plaintext/ciphertext example reuses one buffer for successive stages. If another thread sends before encryption completes, plaintext may escape. Separating buffers, defining ownership and synchronization, and clearing appropriate storage reduce accidental cross-stage use; two buffers alone do not establish ordering if either is still shared without a protocol.

Locks, semaphores, and transactions can create the needed ordering but have scope, performance, and failure-handling costs. Tests should vary schedules and adversarially stress the vulnerable window. Failure to reproduce a timing bug is weak evidence of absence. The source's concurrency-trend discussion and Herb Sutter reference motivate systematic reasoning rather than relying on a favorable scheduler.

\begin{takeaway}
Protect the complete invariant-preserving operation. A check does not remain valid automatically. Prefer stable object identities to repeated path resolution. Establish a single locking or ownership discipline for shared state. Attacker-controlled schedules turn rare interleavings into security-relevant cases.
\end{takeaway}

\subsection{From requirements to architecture and detail}
The lecture cites ISO/IEC~12207:2008 to distinguish architectural design, which allocates requirements to components and their relationships, from detailed design, which makes implementation and verification possible. Choosing a language, framework, database, and API boundary is therefore part of security design, not merely an implementation preference.

Security principles have long been available; the engineering task is to apply them to a specific system and make the resulting choices reviewable. Web, local, GUI, and setuid applications expose different capabilities and failure modes. A checklist is useful when interpreted in that context.

\subsection{Three starting points for threat analysis}
An \textbf{attacker-centric} analysis starts with an adversary's goals and possible entry paths. A \textbf{design-centric} analysis walks the modeled components, data flows, and trust boundaries. An \textbf{asset-centric} analysis starts from entrusted assets and asks what can happen to them. These are perspectives, not mutually exclusive security properties.

\module{Security engineering across the software life cycle}{sec:sdl}

\subsection{A repeatable engineering process}
Software engineering combines technical and management practices to create and maintain software. Traditional phases---requirements, design, implementation, testing, deployment, and maintenance---do not automatically provide security. If a security decision is postponed until late testing, repairing it may require redesigning earlier work rather than changing one line.

The lecture identifies three essential ingredients: a repeatable process, engineer education, and metrics/accountability. A secure development lifecycle (SDL) adds security activities to the ordinary development method. Its goal is to reduce design, implementation, and documentation vulnerabilities and find them early, not to replace all engineering with a final penetration test.

\subsection{Security work products by phase}

\module{Secure development models, capability, and assurance}{sec:models}
\source{SSA - 14 - Secure_Software_Development.pdf}{1--50}
\subsection{Process models and four areas of work}
A secure process is a set of activities for developing, maintaining, and delivering a secure solution; activities may be iterative or concurrent. A process model supplies reference practices and a structure for improvement and assessment. It describes desirable process characteristics without necessarily prescribing an operational method, tool, or detailed implementation.

The lecture distinguishes four SDLC focus areas. \textbf{Security engineering} includes requirements, design, secure coding, review, analysis, and testing. \textbf{Assurance} evaluates artifacts and evidence through verification, validation, expert review, and assessment. \textbf{Organizational/project management} supplies sponsorship, roles, policies, resources, planning, and tracking. \textbf{Risk identification and management} prioritizes exposure and mitigation. A team cannot replace the other three merely by running a code scanner. The system-life-cycle figure on p.~9 places investigation and analysis before logical/physical design, implementation, and maintenance, emphasizing that software work sits in a wider system context.

\subsection{Capability and maturity models}
A capability maturity model identifies mature practices, goal-level definitions, and potential improvements. An appraisal compares actual practice with the reference and asks whether the process is specified, implemented, and institutionalized. A maturity judgment is about a process; a particular product still needs its own evidence. The cost/capability diagram on p.~12 contrasts simple downsizing, which can reduce both cost and capability, with process improvement, which aims to shift the achievable cost/capability relationship. It is a conceptual trade-off, not measured cost data for a particular project.

The source surveys CMMI, FAA-iCMM, Trusted CMM, and SSE-CMM. Its adoption statistics and descriptions such as ``latest'' are historical; in particular its CMMI figures are explicitly dated December~2005. They are not a survey of present-day uptake.

\textbf{CMMI.} The supplied diagram groups practices into process management, project management, engineering, and support. Process management covers organizational process focus, definition, training, performance, and innovation/deployment. Project management covers planning, monitoring/control, supplier agreements, integrated management, risk, teaming, integrated supplier management, and quantitative project management. Engineering covers requirements development/management, technical solution, integration, verification, and validation. Support covers configuration, process/product quality assurance, measurement/analysis, organizational integration environment, decision analysis, and causal analysis.

\textbf{iCMM.} The FAA-oriented integrated model aims at enterprise-wide improvement. Its source list combines ISO~9001:2000, EIA/IS~731, award criteria, CMMI variants, ISO/IEC TR~15504, ISO/IEC~12207, and a cited draft of ISO/IEC~15288. SSAM, the SSE-CMM appraisal method discussed in the slides, establishes a baseline and momentum for improvement. A mature organization is more likely to generate useful, repeatable evidence, but an immature organization can produce a high-assurance product. Conversely, a mature process can still produce a vulnerable product. Do not reverse an association into a product-level logical guarantee.

\module{Building security in: risk management and touchpoints}{sec:building-in}
\source{SSA - 15 - Building Security IN.pdf}{1--44}
This deck revisits the premise that software should continue to function correctly under malicious attack. Connectivity, extensibility, and complexity increase exposure; implementation bugs and deeper design flaws both contribute to risk. It frames software security through three mutually supporting pillars: applied risk management, software-security touchpoints, and reusable security knowledge. This module extends the lifecycle and process material in Sections~\ref{sec:sdl} and~\ref{sec:models} with the risk-management loop and artifact-level practices.

\subsection{Risk management as a continuous loop}
The five-stage risk-management framework begins by understanding the business context: goals, stakeholders, priorities, and constraints. It then identifies business and technical risks, connects technical weaknesses to potential business impact, synthesizes and ranks the risks, chooses a cost-effective mitigation strategy, and carries out fixes with validation. Likelihood, impact, and mitigation progress inform prioritization. The framework does not prescribe a universal scoring formula; severity needs to be expressed in the project context.

Risk analysis is not a one-time gate. New risks can appear during any SDLC phase, and a finding during mitigation may require revisiting earlier assumptions. The five stages can be applied at project, phase, and artifact levels. Each iteration should retain the rationale for priority, the selected treatment, its validation evidence, and any accepted residual risk.

\subsection{Touchpoints and their limits}
The deck's seven software-security touchpoints are code review, architectural risk analysis (also called threat modeling or security design analysis), penetration testing, risk-based security testing, abuse cases, security requirements, and security operations. The source presents code review and architectural analysis as especially effective based on experience, while noting their order may be swapped. Code review finds implementation bugs but cannot establish that the architecture is sound. Architectural analysis can expose design flaws that are difficult to infer from individual lines of code. Penetration testing is a useful but bounded view of the implementation under its rules of engagement.

Touchpoints are process-agnostic: they can be incorporated into different development models and may be adopted together. A penetration-test-first approach is reactive; skipping either code review or architecture analysis leaves a different class of risk less examined. Risk-based tests should derive from the identified threats and requirements, and operations should feed incidents and observations back into risk analysis.

\module{Smart contracts and decentralized execution}{sec:contracts}
\source{SSA - 16 - Smart Contracts.pdf}{1--28}
The lecture motivates smart contracts with a notarization problem. In a conventional design, a trusted notary validates and signs a document, and a secure archive preserves it. Automating the notary centralizes code and records in a server that can be compromised, creating integrity and availability risks and adding trust in banks and servers. The proposed alternative decentralizes validation and record keeping through a blockchain. This changes the trust model; it does not remove the need to reason about code, consensus, keys, and economic incentives.

\subsection{Blocks, transactions, and consensus}
A blockchain is a growing sequence of blocks. In the Ethereum model introduced by the slides, accounts are associated with public-key-derived addresses; signed transactions update balances and contract state. A transaction is valid only if its signature verifies and the sender satisfies balance and other execution rules. Blocks include transactions and information, such as a previous-block hash, used to check validity.

The deck names persistence, liveness, and public verifiability as desired blockchain properties and relates their guarantees to a bound on corrupted consensus participants. The exact corruption threshold depends on the consensus protocol; it is not a universal property of every blockchain. In the proof-of-work example, a proposer searches for a nonce so a hash of the prior block and nonce falls below a target. Other nodes verify the work and block contents before accepting the block. The source's proof-of-work example is a teaching model, not a complete account of current Ethereum consensus.

\subsection{Contracts as stateful programs}
A deployed contract has an address, code, and persistent state. Users invoke its functions by transactions, optionally transferring the chain's native currency. Nodes execute contract code in a virtual machine and update the resulting state as part of block processing. Contract composition enables one contract to call another, so a security review must include external calls and assumptions about interacting code.

For contract calls, execution computes a state transition from the current state and transaction. The slide sequence shows that other nodes rerun the contract and reject a proposed update if the sender cannot pay the required amount. The proposer proposes a transition; it does not unilaterally determine the accepted state.

The token sketch illustrates a balance mapping and an exchange operation. It is intentionally schematic: the expression comparing payment and token quantity does not by itself define a sound conversion, and the sketch omits access control, integer bounds, event semantics, and failure handling. Contract state and transactions are public in the model, so sensitive information should not be placed on-chain merely because an access modifier hides a getter.

\subsection{Consensus examples and security properties}
The deck introduces persistence (accepted blocks remain available and are not modified under the model), liveness (a valid transaction eventually appears in a block), and public verifiability (participants can obtain and check the chain). Its stated corruption threshold differs by consensus assumptions, so the slides' one-third or one-half figures must not be detached from the protocol model.

In the proof-of-work sketch, a proposer varies a nonce in a candidate block until the hash of the previous-block value and nonce is below a target. Other nodes can verify the successful result much more cheaply than searching for it. A coinbase transaction rewards the successful proposer. The lecture also outlines proof of stake: validators lock stake, block-proposer selection depends on stake, and rewards and the possibility of losing locked value are meant to shape incentives. These are two consensus examples, not interchangeable algorithms.

Decentralization changes who must be trusted, but the smart contract remains ordinary developer-written software running in an execution environment. The slides emphasize adapting familiar code-review, analysis, and fuzz-testing methods to the contract and virtual-machine setting. \module{Re-entrancy as a contract control-flow flaw}{sec:reentrancy}
\source{SSA - 17 - Re-entrancy attack.pdf}{1--11}
Re-entrancy occurs when contract A calls external contract B before A has completed a state update. B's fallback or callback can call A again while A still exposes the old state. The pattern resembles a race in that execution re-enters an operation at a vulnerable point, although it is a synchronous call sequence rather than necessarily two concurrent threads.

\subsection{The withdraw example}
The supplied \texttt{DepositFunds} contract reads the caller's recorded balance, sends that amount with an external call, and only afterward sets the balance to zero. A malicious recipient's fallback calls \texttt{withdraw} again before the first invocation has executed the state update. Each nested call observes the same positive balance and can send it again, draining funds held by the contract.

The attack is an execution-order problem. First, the attacker deploys a recipient contract whose fallback re-enters the victim. The attack contract deposits one ether and starts a withdrawal. The victim checks the recorded balance, sends one ether, and yields control to the recipient. Because the victim has not yet cleared the recorded balance, the callback passes the same check and starts another withdrawal. This repeats while the victim contract still holds enough ether for the attacker's callback condition.

The trace abstracts gas costs, transaction rollback, and exact EVM call-depth constraints; it isolates the balance-ordering defect shown in the lecture. The attacker stops when the fallback condition fails or execution otherwise cannot continue.

\begin{lstlisting}[language=Java]
// Vulnerable ordering from the slide, shown schematically.
uint bal = balances[msg.sender];
require(bal > 0);
(bool sent, ) = msg.sender.call{value: bal}("");
require(sent);
balances[msg.sender] = 0;
\end{lstlisting}
The key defect is the order of effects and external interaction, not a failure of the initial balance check. A checks-effects-interactions design validates conditions, commits the internal state transition, and only then makes an external call, with careful handling of failed transfers. A re-entrancy guard can also prevent a function from being re-entered while it is active. Neither pattern removes the need to review all externally reachable functions and cross-contract call paths.

The slide's guard is a lock around the protected body: reject the call when already locked, set the lock, run the function, then clear the lock. That mechanism depends on applying the guard consistently to the relevant entry points. State-before-call ordering addresses the stale-state condition directly; a guard blocks recursive entry. They are complementary reasoning patterns in the lecture.

The deck connects re-entrancy to the DAO incident and later historical incidents. Those examples show that the flaw class persisted across changing contracts and protocols; their reported amounts and dates are historical claims from the slides. The takeaways also stress that public code and state create confidentiality challenges, and that correctness depends on both contract and EVM behavior.

The source describes callbacks and fallback functions as enabling a form of re-entry that can resemble interleaving. It is useful to relate the example to the race-condition lecture, while keeping the execution model distinct: this attack is a nested synchronous call that exposes intermediate state, not necessarily a second operating-system thread. The source also raises confidentiality: code and state are public in the basic chain model; it mentions zero-knowledge proofs with encrypted data as an emerging direction and warns that bugs in the contract or EVM can undermine such protections.

\module{Solidity, gas, and token interfaces}{sec:solidity}
\source{SSA - 18 - Introduction to Solidity.pdf}{1--72}
This supplemental deck is attributed on its title slides to Dan Boneh, Arthur Gervais, Andrew Miller, Christine Parlour, and Dawn Song, and links to \href{https://defi-learning.org}{defi-learning.org}. It presents smart contracts as neither intrinsically smart nor equivalent to legal contracts: from a programmer's perspective they are programs with persistent storage deployed to a blockchain. Contracts can expose methods, enforce conditions, hold native currency, and interact with other contracts.

\subsection{Solidity and the Ethereum execution model}
Solidity is a statically typed high-level language compiled to EVM bytecode. The slides introduce integer types, arrays, strings and bytes, and mappings from keys to values. A mapping does not provide a built-in way to enumerate nonzero entries or determine its length, so designs needing iteration require additional state. Function visibility controls who can invoke an operation; mutability modifiers describe whether it reads or changes state. Neither \texttt{private} visibility nor a hidden field makes on-chain data confidential.

The distinction between a contract class and a deployed object is important. The source defines code and storage declarations; deployment creates a contract instance at an address with initial state. A later call names the instance and a method, supplies arguments, and may transfer native currency. Each node applies the same deterministic execution to the accepted prior state and transaction in the model described by the slides.

The deck's domain-name registry example shows a caller invoking \texttt{registerDomain} with a name such as \texttt{defi.io}; the registry updates the owner in contract storage, and a later query returns the current owner.

The example prompts questions about what is missing: who may register or replace a name, whether ownership can be transferred, what happens on duplicate names, and what other functions are necessary. The source presents this as a design exercise, not as a complete registry specification.

Constructors initialize a contract instance. \texttt{require} can reject a call whose authorization or state preconditions are not met. View functions and event logs provide ways to observe state. The slides also introduce interfaces and calls to external contracts, the native currency and its smallest unit (wei), block time and other metadata, and storage, memory, and calldata as different data locations. The short code examples are instructional and should be checked against the compiler version and exact Solidity syntax intended for deployment.

Function signatures combine a name, argument types, return types, visibility, and mutability. Integer declarations include signed and unsigned fixed-width types. The deck emphasizes that conversions behave more like C than Python: changing width or signedness can alter values, so conversion questions need explicit reasoning. Arrays may be fixed-size or dynamic; storage arrays persist across transactions, while dynamically sized data has additional cost. Strings and byte arrays are distinct representations, and the slides use \texttt{abi.encode} to flatten values into bytes. These features make types and representation part of contract security, not just syntax.

External-contract interfaces describe how to invoke another contract at a supplied address. Inheritance, interfaces, and creating contracts programmatically allow composition; each adds dependencies and reachable behavior. The slides' quiz asks students to explain what code does and identify what is wrong, reinforcing that reading a declaration is not a substitute for tracing state and caller privileges.

\subsection{Gas and failure behavior}
Transactions pay for computation in gas. The amount depends on executed EVM operations, and more complex execution consumes more gas. A transaction specifies a gas limit and price; unused gas is refunded, while an out-of-gas execution reverts state changes from the transaction but still charges for work already performed. Blocks also have a total gas limit, which constrains aggregate execution. Gas therefore affects both cost and availability: an operation that is too expensive may fail for callers, and unbounded loops over growing state can make a function unusable.

The slides illustrate a transaction reserving a limit and price up front, then decrementing a remaining-gas counter as instructions execute. The cost table is indexed by compiled EVM opcodes; some costs depend on arguments. This is why high-level source length alone does not predict transaction cost. A transaction that runs out of gas raises an exception and rolls back state changes and transfers from that execution, but the caller still pays for instructions consumed before failure. The slides note that exceptions may be caught and that a callee can be given only part of the available gas.

\subsection{Auctions, legal agreements, and tokens}
The Dutch auction case study models a price that begins high and declines over time until a buyer accepts. To reason about it as a contract, identify the offer, acceptance transaction, consideration, agreement, and the capacity/legal conditions that remain external to code. Automatic execution can reduce dependence on intermediaries for digital assets, but it does not establish that the encoded rules reflect the parties' intended or legally enforceable agreement.

The source's comparison maps a token sale to familiar agreement elements: an offer states the exchange terms; acceptance is expressed by digitally signing a transaction; consideration is transferred in the chain's native currency; and the contract can move a pre-deposited digital asset in the same transaction. Mutual agreement is related to publishing the high-level code. Capacity and legality are not established by successful execution, so a functioning program cannot alone settle the parties' intent or the legal status of the arrangement.

This is a qualitative drawing of the deck's Dutch-auction rule; no price schedule or numeric formula is supplied in the source. The contract's timing and acceptance conditions still need precise specification.

The token slides distinguish fungible assets, which are interchangeable, from non-fungible assets, each with a distinct identifier or attributes. Standard interfaces make generic interactions possible. The deck cites ERC-20 functions such as \texttt{totalSupply}, \texttt{balanceOf}, and \texttt{transfer}, plus allowance functions \texttt{approve} and \texttt{transferFrom}; it also discusses NFTs and ERC-721. Interface conformance improves interoperability, but a standard interface does not guarantee safe authorization, correct accounting, or safe composition with other contracts. The slides' Ropsten and wallet walkthrough is a historical demonstration and is not current deployment guidance.

The allowance interface separates owner authorization from spender execution: an owner approves a quantity, a spender may later use the allowance through \texttt{transferFrom}, and \texttt{allowance} reports the remaining amount. This delegation supports composing contracts, but creates a permission that users and reviewers must understand. Fungible balances aggregate interchangeable units; a non-fungible token instead associates a distinct identifier and attributes with an asset. The deck's standard-interface point is interoperability: a common method contract lets other programs call tokens generically, while the implementation remains responsible for preserving its own accounting and permission invariants.

\module{Language-based security and type safety}{sec:language-security}
\source{SSA - 19 - Language-Based Security.pdf}{1--42}
\source{SSA - 19 - Language-Based Security (part 2).pdf}{1--36}
Programming languages can constrain what a program can do and make security properties easier to reason about. The two supplied part-19 decks overlap in their introduction to safety and types; these notes combine the repeated material with the second deck's more formal Mini-C account. Safety concerns protection from accidental failures, while security concerns failures induced by an active attacker, though the distinction is not absolute.

\subsection{Abstractions and dimensions of safety}
Language constructs abstract machine instructions, types abstract data representation, and procedures abstract the call stack. Operating systems similarly abstract memory and processor access through processes and virtual memory. These abstractions reduce complexity and support access control only while the implementation enforces them. A stack overwrite can break the call abstraction; uninitialized memory can disclose information; timing can expose behavior that an abstraction was expected to hide.

\node[box,text width=30mm,right=of app](runtime){Compiler and\\execution engine};
\node[box,text width=30mm,right=of runtime](os){OS processes,\\virtual memory};
\node[box,text width=30mm,right=of os](machine){Hardware and\\physical resources};
\draw[arr](app)--(runtime);\draw[arr](runtime)--(os);\draw[arr](os)--(machine);
\node[lab,below=5mm of runtime,text width=60mm]{Each guarantee depends on the abstraction below enforcing its contract.};
\end{tikzpicture}\end{center}
\diagramcaption{Language and operating-system abstractions layer security guarantees over hardware.}

The slides describe a safe language as one whose abstractions are enforceable, whose semantics are precise, and whose behavior can be understood modularly. Safety has several dimensions: memory, types, threads, arithmetic, nullness, and aliasing. The guarantee can also vary in strength, from converting arbitrary code execution into a controlled exception to rejecting an unsafe operation statically. Compile-time checks, runtime bounds checks, garbage collection, and a verified execution engine provide different layers of enforcement.

Memory safety rules out access to unallocated or deallocated memory; some definitions also rule out reading uninitialized memory. Unchecked array bounds, pointer arithmetic, null dereferences, and manual allocation can undermine it. In C, dereferencing a null pointer has undefined behavior, not a guaranteed crash. Managed languages still rely on a trusted computing base that includes their runtime and verifier; native components, unsafe blocks, VM defects, or unsound type checking can reopen memory-corruption risks.

The slide's \texttt{scanf} example makes the type issue concrete: a function accepts a parameter written as \texttt{char str[]}, then reads a string of unbounded length into it. At the call site, the actual array may be only eight bytes. The parameter declaration does not carry that bound into the function, so a call can be well-typed in C and still overflow the object.
\begin{lstlisting}[language=C]
void readstring(char str[]) { scanf("%s", str); }
void main(void) { char buf[8]; readstring(buf); }
\end{lstlisting}
The problem is not merely that C uses types. It permits unsafe conversions and loses relevant size information at this interface. A type system can guarantee only properties its rules preserve and its implementation enforces.

\subsection{Types, soundness, and the trusted runtime}
Types specify expected data and code behavior. A type checker can reject certain programs without executing them, but the presence of types alone does not imply type safety: C permits operations and casts that can break its type abstractions. A type-safe language aims to guarantee that well-typed programs continue to behave according to the language semantics rather than getting stuck in an invalid operation.

The second part-19 deck introduces Mini-C, a deliberately small language without functions, pointers, structures, or casts. Its expression and command semantics define which reductions are allowed; for example, an ill-typed expression such as multiplying a Boolean by an integer has no evaluation rule. Typing rules describe valid expressions and commands. The safety theorem then states that a well-typed command in a well-typed memory either has completed or can continue reducing. This links a static check to an operational definition of safe execution.

\begin{concept}{What the Mini-C theorem establishes}
For a well-typed command $c$ and a well-typed memory $\sigma$, every permitted reduction step must leave a configuration that is not stuck. A stuck state is neither the completed command nor a state with a valid next step. This does not say that the program terminates, computes the intended answer, or is secure against every kind of attacker.
\end{concept}

The proof separates two obligations: a well-typed program can take a step unless it is finished (progress), and a step preserves the typing invariant (preservation). The source formulates the result through its Mini-C reduction relations. The diagram summarizes the argument, not a claim that ordinary compiler checks alone prove the theorem for arbitrary production languages.
\begin{center}\begin{tikzpicture}[node distance=6mm,every node/.style={font=\small}]
\node[box,text width=42mm](check){Typing rules accept\\program and memory};
\node[box,text width=42mm,right=of check](step){Operational semantics\\takes one step};
\node[box,text width=42mm,right=of step](safe){Typing invariant\\is preserved};
\draw[arr](check)--node[above,lab]{progress}(step);\draw[arr](step)--node[above,lab]{preservation}(safe);
\draw[arr](safe.south) to[out=-90,in=-90,looseness=1.3] node[below,lab]{repeats until completion; never gets stuck} (step.south);
\end{tikzpicture}\end{center}
\diagramcaption{Progress and preservation are the two proof obligations behind the Mini-C safety result.}

The proof idea is stronger than testing examples: preserve the invariant that memory values match their declared types and show each permitted computation step preserves that property. Real languages require a much larger semantics and trusted compiler/runtime implementation. The slides discuss representation independence as another way to state that the concrete encoding of a value should not change program behavior.

The source proposes comparing a typed operational semantics, which records and checks type information during execution, with an untyped semantics that does not. If the two give equivalent behavior for every well-typed program, the run-time representation should not let an accepted program distinguish encodings that the language treats as the same value. This is a proof obligation about the formal language and its execution, not something inferred from a few successful tests.

\subsection{Beyond basic types}
Type systems and language design can also express non-null values, array bounds, information-flow restrictions, access control, protocol correctness, and alias restrictions. Visibility and immutability reduce some classes of interaction, while safe arithmetic specifies what happens on overflow. Thread safety remains a distinct obligation: unsynchronized shared mutable state can produce unexpected results even in a memory-safe language. Immutable values reduce mutation hazards, but do not replace a correct concurrency model.

The thread-safety slides show why publication order matters. Construction can be viewed as allocating an object, writing a field, and publishing a reference. If an implementation permits publication to become visible before initialization, another thread can observe the default field value. The deck uses a Java example and notes that a \texttt{final} field addresses that particular initialization case under the Java memory-model rules it discusses; the lesson is not a universal repair for data races. Shared mutable aliases can also invalidate a caller's assumption between a check and a later use, even in a single-threaded call sequence.

\module{Information flow and non-interference}{sec:information-flow}

\source{SSA - 20 - Information Flow.pdf}{1--36}
Information-flow security constrains what happens to data after a program has accessed it. Access control asks whether a principal may read an object; information-flow control asks whether the data may influence a later output or state. The motivating phone example allows location to flow to a hotel-search service and payment details to the hotel, while forbidding other disclosures. Information-flow policies can express confidentiality (prevent disclosure) and integrity (prevent untrusted input from controlling trusted state).

\subsection{Explicit, implicit, and covert flows}
With high (secret) and low (public) labels, an assignment from a high value to a low variable is an explicit flow. Printing a high variable is also an explicit disclosure. For integrity, assigning low-integrity input into a high-integrity variable can corrupt trusted state; the direction is reversed from confidentiality.

The lecture's basic examples distinguish permitted and prohibited operations by the policy being enforced:
\begin{center}\small
\begin{tabularx}{\linewidth}{@{}p{28mm}YY@{}}\toprule
Operation & Confidentiality reading & Integrity reading\\\midrule
\texttt{lo = hi} & Secret data is copied into public state: a direct leak. & Low-integrity data influences high-integrity state: untrusted input is promoted.\\
\texttt{hi = lo} & Public data is placed in secret state: usually no disclosure. & Trusted state receives high-integrity data: usually permitted.\\
\texttt{println(hi)} & Secret output is directly observable: a leak. & Outputting trusted data does not by itself corrupt it.\\
\texttt{readln(hi)} & Reading into a secret variable does not disclose its old value. & Untrusted input written into a trusted variable is dangerous.\\\bottomrule
\end{tabularx}\end{center}
The direction changes because confidentiality protects information from flowing outward, while integrity protects trusted decisions from being influenced by untrusted information. The source explicitly warns that labels alone do not determine whether every input or output is a violation; the required policy and observable sink matter.

Control flow can leak even without copying the secret. In \texttt{if (high > 0) low = 99;}, observing whether the public variable changes reveals a property of the secret guard. This is an implicit flow. Termination, execution time, exceptions, and memory-access behavior can also act as hidden or covert channels. For example, a loop whose number of iterations depends on a secret may reveal it through timing, and an array exception can reveal information about an index or array length.

The direct arrows capture assignments such as \texttt{lo=hi} and output such as \texttt{println(hi)}. The lower route captures control-dependent behavior: the value need not be copied to \texttt{lo} for an observer to learn something about the secret. A data-flow tool that tracks only assignments may miss that lower route.

\subsection{A lattice-based type discipline}
The slides model security levels with a lattice; in the two-level case, $L\le H$, where $L$ is public and $H$ is secret. A larger level permits more confidential information. More complex labels can represent categories or compartments, such as classified information associated with particular countries. The lattice join gives the least level that can contain information from two inputs.

\begin{center}\begin{tikzpicture}[node distance=12mm,every node/.style={font=\small}]
\node[box,text width=30mm](low){$L$\\Public};
\node[box,text width=30mm,above=of low](high){$H$\\Secret};
\draw[arr](low)--node[right,lab]{$L\le H$}(high);
\node[lab,right=18mm of high,text width=50mm,align=left]{Information may move upward to a more restrictive label.\\A high value may not flow downward to a public sink.};
\end{tikzpicture}\end{center}
\diagramcaption{The two-level confidentiality lattice allows information to flow upward, not downward.}

Expression judgments $\gamma\vdash e:t$ record the level of information an expression may contain in context $\gamma$, the labels assigned to variables. Combining expressions takes account of both operands; subtyping permits an expression at a lower level to be treated as more restrictive, not the reverse. A command judgment $\gamma\vdash c:\mathrm{cmd}\ t$ describes which levels the command may write. Assignment must not write a high expression into a low variable. For a conditional, the guard is also information: both branches must obey a write restriction that includes the guard's level. Sequential composition and loops propagate the relevant restrictions.

Command subtyping reverses the order: a command allowed to write only at a high level is also safe under a more restrictive write obligation, while a command that may write low cannot be silently promoted to one that promises high-only writes. This is the source's anti-monotonicity observation. The rules resemble Bell--LaPadula's ``no read up'' and ``no write down'' discipline for mandatory access control, but here they type-check a program's use of variables rather than monitor a process's access to files.

These rules can be sound yet incomplete: some harmless programs are rejected, such as a branch guarded by a constant false condition, a value computed as \texttt{hi + 1 - hi}, or a secret-dependent assignment overwritten before any observation. Soundness needs a semantic definition of leakage. Write $\mu\sim_L\nu$ when memories $\mu$ and $\nu$ agree on all low variables. Termination-insensitive non-interference requires that whenever both executions terminate, their resulting low parts still agree:
\[
\mu\sim_L\nu\quad\Longrightarrow\quad
\operatorname{low}(\operatorname{Exec}(C,\mu))=
\operatorname{low}(\operatorname{Exec}(C,\nu)),
\]
for the terminating executions in the source's definition. A type system is sound with respect to this property if every well-typed program satisfies it. This semantic statement is stronger than saying that no suspicious assignment was found: it compares executions from states that differ only in secret data.

\begin{center}\begin{tikzpicture}[node distance=8mm,every node/.style={font=\small}]
\node[box,text width=40mm](left){Run $C$ from $\mu$\\low values $l$, high value $h_1$};
\node[box,text width=40mm,right=of left](right){Run $C$ from $\nu$\\same low values $l$, high value $h_2$};
\node[box,text width=44mm,below=of $(left)!0.5!(right)$](compare){Compare public observations\\must match for non-interference};
\draw[arr](left)--(compare);\draw[arr](right)--(compare);
\end{tikzpicture}\end{center}

The termination-insensitive definition compares results only when both executions terminate, so it ignores a termination channel. Termination-sensitive non-interference additionally requires both executions to terminate or diverge together. A stricter loop typing rule can block some termination leaks, but is correspondingly restrictive. Exceptions, nondeterministic scheduling, and probabilistic outcomes require richer semantic definitions; the slides introduce possibilistic non-interference for nondeterministic programs and note that repeated observations may reveal distributional information.

The difference is observable even when the final low variables match: if a secret guard makes one execution loop forever and another terminate, an observer learns which case occurred. A termination-sensitive definition therefore requires the runs to agree on termination as well as on low results. The source notes that a stricter while rule requires a low-level guard and low-level body to assign a low-level command; a corresponding change is needed for conditionals. This can close the channel but rejects useful programs whose termination depends on secrets.

With nondeterministic execution, such as scheduling, one run may have several outcomes. The source's possibilistic definition asks whether each low-observable terminating outcome in one state is possible from the other low-equivalent state. This still ignores probabilities. If two secret states produce overlapping outputs with different probabilities, one observation may reveal nothing while repeated observations let an adversary estimate the distribution. Thus the observer model must specify whether it sees one result, termination, timing, exceptions, scheduling outcomes, or repeated-run frequencies.

\subsection{Practical enforcement and declassification}
Static systems such as JFlow/Jif can encode information-flow policies but may demand substantial annotations and reject useful programs. Taint analysis often tracks integrity from input to sensitive sinks; dynamic tainting can enforce similar restrictions at runtime. Practical tools commonly approximate the property and may be unsound or incomplete, and often focus on explicit flows rather than implicit dependencies.

Real systems need controlled declassification: an approved operation may release an encryption result derived from a secret, or a validated input may be treated as trusted after a check. The declassification rule must be explicit and scoped. Without it, useful programs can be rejected; if it is too broad, it becomes an unexamined bypass of the policy.

The source's practical examples distinguish static and dynamic enforcement. JFlow/Jif expresses and checks information-flow restrictions for Java, with substantial annotation and design effort. Static analysis tools can track tainted data toward sinks, for example to detect SQL injection, but may be limited to an intra-procedural view and may prioritize integrity over confidentiality. Dynamic tainting, as illustrated for Perl, follows marked input during execution. Practical checkers may trade soundness or completeness for usability and often pay less attention to implicit flows.

\begin{takeaway}
Information-flow claims need a stated attacker observation model. Track both data dependencies and control dependencies, decide whether timing and termination count as observations, and record any approved declassification. Access restrictions alone do not control how accessed data later influences behavior.
\end{takeaway}

Lattice & A partially ordered set with pairwise least upper and greatest lower bounds.\\
Join & Least upper bound, combining possibilities while retaining the best available common precision.\\

Gas & Metered unit of EVM computation used to bound and price transaction execution.\\
Type safety & Property that well-typed programs continue according to the language's defined semantics without getting stuck in an invalid operation.\\
Information flow & Allowed or forbidden influence of data on later outputs, state, or observable behavior.\\
